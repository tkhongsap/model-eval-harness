# Token Factory API Guide

**Document version:** 1.0.0 \
**API version:** 1.0.0 POC \
**Last updated:** 2026-08-14 \
**Audience:** Approved External Business Units \
**Support and key lifecycle:** [Thanawat.Kaewboworn@truecorp.co.th](mailto:Thanawat.Kaewboworn@truecorp.co.th)

Token Factory provides an OpenAI-compatible HTTPS API for approved business-unit use cases. This guide covers onboarding, authentication, model discovery, Responses, Chat Completions, streaming, errors, limits, and data handling.

> Token Factory is a POC service. Support is best effort. There is no formal SLA or backward-compatibility commitment during the POC.

## Quick start

Before making a request, you need:

1. **API key** — provided by Token Factory for your approved use case.
2. **Model ID** — the exact `id` returned by `GET /v1/models` for your key. It identifies the model to call; it is not an API key.

The Token Factory base URL is fixed:

```bash
export TOKEN_FACTORY_BASE_URL='https://token-fac-api.truecorp.co.th'
```

### 1. Load your API key

Load the key from your approved secret store. Do not paste it into source code, tickets, chat, or screenshots.

```bash
read -s -p 'Token Factory API key: ' TOKEN_FACTORY_API_KEY; echo
export TOKEN_FACTORY_API_KEY
```

### 2. Check which models your key can use

```bash
curl --fail-with-body --silent --show-error \
  "$TOKEN_FACTORY_BASE_URL/v1/models" \
  -H "Authorization: Bearer $TOKEN_FACTORY_API_KEY"
```

Look in the returned `data` list and copy the exact value of one `id` assigned to your use case:

```json
{
  "data": [
    { "id": "<MODEL_ID_RETURNED_TO_YOU>" }
  ]
}
```

Set that value as your model. For this first text request, choose a text-generation model. If you are unsure which model to select, contact Token Factory support.

```bash
export TOKEN_FACTORY_MODEL='<PASTE_MODEL_ID_HERE>'
```

### 3. Make your first request

```bash
curl --fail-with-body --silent --show-error \
  "$TOKEN_FACTORY_BASE_URL/v1/responses" \
  -H "Authorization: Bearer $TOKEN_FACTORY_API_KEY" \
  -H 'Content-Type: application/json' \
  -d "{
    \"model\": \"$TOKEN_FACTORY_MODEL\",
    \"input\": \"Reply with exactly: TOKEN FACTORY READY\",
    \"max_output_tokens\": 32,
    \"temperature\": 0
  }"
```

If the request succeeds, the response is JSON generated by the selected model. Keep using the same base URL, API key, and model ID in your application.

Clear the sensitive shell variable when you finish:

```bash
unset TOKEN_FACTORY_API_KEY
```

## Onboarding

Before integration:

1. Send the use-case name, BU name, technical contact, expected traffic pattern, and fixed outbound source IP to Token Factory support.
2. Complete the network and use-case approval process for your BU.
3. Receive a virtual API key through an approved secret-delivery channel.
4. Verify strict HTTPS connectivity and call `GET /v1/models`.
5. Use only the models returned for your key.

An API key does not constitute Security, RAI, data, or business approval. Data sent to the API must remain within the approvals held by the calling BU and use case.

## Base URL and public interface

Base URL:

```text
https://token-fac-api.truecorp.co.th
```

Supported public methods:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/v1/models` | Discover models available to the current key |
| `POST` | `/v1/responses` | Generate output using the supported Responses subset |
| `POST` | `/v1/chat/completions` | Generate output from chat-formatted messages |

Token Factory does not expose API-key management methods to BU clients. Request new, renewed, rotated, or revoked keys through the support contact.

The machine-readable contract is provided in [openapi.yaml](openapi.yaml).

## Authentication

Every request requires an HTTP bearer token:

```http
Authorization: Bearer <TOKEN_FACTORY_API_KEY>
```

Use a server-side secret manager or protected environment variable. Never place a key in:

- browser or mobile application code;
- public repositories or build artifacts;
- client-side JavaScript bundles;
- URLs, query strings, logs, or analytics events;
- email, chat, screenshots, or support tickets.

Use a separate key for each approved BU use case. If a key might be exposed, stop using it and request revocation and replacement.

## Model discovery

`GET /v1/models` is the authoritative source for model identifiers available to your key. The catalog is dynamic and is not a compatibility guarantee.

```bash
curl --fail-with-body --silent --show-error \
  "$TOKEN_FACTORY_BASE_URL/v1/models" \
  -H "Authorization: Bearer $TOKEN_FACTORY_API_KEY"
```

Example response shape:

```json
{
  "object": "list",
  "data": [
    {
      "id": "<MODEL_ID>",
      "object": "model",
      "created": 0,
      "owned_by": "token-factory"
    }
  ]
}
```

Clients should select an `id` at runtime or keep it in configuration. Do not hard-code an assumed catalog into application logic. A new model is provisioned to a BU only after internal capability testing.

## Responses API

Use `POST /v1/responses` for a simple input-to-output workflow.

### cURL

```bash
curl --fail-with-body --silent --show-error \
  "$TOKEN_FACTORY_BASE_URL/v1/responses" \
  -H "Authorization: Bearer $TOKEN_FACTORY_API_KEY" \
  -H 'Content-Type: application/json' \
  -d "{
    \"model\": \"$TOKEN_FACTORY_MODEL\",
    \"input\": \"Summarize the benefits of API key rotation in three bullets.\",
    \"max_output_tokens\": 160,
    \"temperature\": 0.2
  }"
```

### Python with the OpenAI SDK

Install an OpenAI SDK version that supports the Responses API, then set the Token Factory base URL:

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["TOKEN_FACTORY_API_KEY"],
    base_url="https://token-fac-api.truecorp.co.th/v1",
)

response = client.responses.create(
    model=os.environ["TOKEN_FACTORY_MODEL"],
    input="Reply with exactly: TOKEN FACTORY READY",
    max_output_tokens=32,
    temperature=0,
)

print(response.output_text)
```

### Server-side JavaScript

This example requires Node.js 18 or newer. It must run on a trusted server, never in a browser or frontend bundle.

```javascript
const baseUrl = "https://token-fac-api.truecorp.co.th";
const apiKey = process.env.TOKEN_FACTORY_API_KEY;
const model = process.env.TOKEN_FACTORY_MODEL;

if (!apiKey || !model) {
  throw new Error("TOKEN_FACTORY_API_KEY and TOKEN_FACTORY_MODEL are required");
}

const response = await fetch(`${baseUrl}/v1/responses`, {
  method: "POST",
  headers: {
    Authorization: `Bearer ${apiKey}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    model,
    input: "Reply with exactly: TOKEN FACTORY READY",
    max_output_tokens: 32,
    temperature: 0,
  }),
});

if (!response.ok) {
  throw new Error(`Token Factory HTTP ${response.status}: ${await response.text()}`);
}

console.log(await response.json());
```

## Chat Completions API

Use `POST /v1/chat/completions` when your application already uses role-based chat messages.

### cURL

```bash
curl --fail-with-body --silent --show-error \
  "$TOKEN_FACTORY_BASE_URL/v1/chat/completions" \
  -H "Authorization: Bearer $TOKEN_FACTORY_API_KEY" \
  -H 'Content-Type: application/json' \
  -d "{
    \"model\": \"$TOKEN_FACTORY_MODEL\",
    \"messages\": [
      {\"role\": \"system\", \"content\": \"Answer concisely.\"},
      {\"role\": \"user\", \"content\": \"What is key rotation?\"}
    ],
    \"max_tokens\": 160,
    \"temperature\": 0.2
  }"
```

### Python with the OpenAI SDK

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["TOKEN_FACTORY_API_KEY"],
    base_url="https://token-fac-api.truecorp.co.th/v1",
)

completion = client.chat.completions.create(
    model=os.environ["TOKEN_FACTORY_MODEL"],
    messages=[
        {"role": "system", "content": "Answer concisely."},
        {"role": "user", "content": "What is key rotation?"},
    ],
    max_tokens=160,
    temperature=0.2,
)

print(completion.choices[0].message.content)
```

### Server-side JavaScript

```javascript
const response = await fetch(

```

## Streaming

Set `stream` to `true` to request Server-Sent Events. Process events incrementally and stop when the stream sends its terminal event or `[DONE]`.

```bash
curl --no-buffer --fail-with-body --silent --show-error \
  "$TOKEN_FACTORY_BASE_URL/v1/chat/completions" \
  -H "Authorization: Bearer $TOKEN_FACTORY_API_KEY" \
  -H 'Content-Type: application/json' \
  -d "{
    \"model\": \"$TOKEN_FACTORY_MODEL\",
    \"messages\": [{\"role\": \"user\", \"content\": \"Count from one to five.\"}],
    \"max_tokens\": 64,
    \"stream\": true
  }"
```

Python:

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["TOKEN_FACTORY_API_KEY"],
    base_url="https://token-fac-api.truecorp.co.th/v1",
)

stream = client.chat.completions.create(
    model=os.environ["TOKEN_FACTORY_MODEL"],
    messages=[{"role": "user", "content": "Count from one to five."}],
    max_tokens=64,
    stream=True,
)

for chunk in stream:
    if chunk.choices and chunk.choices[0].delta.content:
        print(chunk.choices[0].delta.content, end="", flush=True)
```

Server-side JavaScript:

```javascript
const response = await fetch(
  "https://token-fac-api.truecorp.co.th/v1/chat/completions",
  {
    method: "POST",
    headers: {
      Authorization: `Bearer ${process.env.TOKEN_FACTORY_API_KEY}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({
      model: process.env.TOKEN_FACTORY_MODEL,
      messages: [{ role: "user", content: "Count from one to five." }],
      max_tokens: 64,
      stream: true,
    }),
  },
);

if (!response.ok || !response.body) {
  throw new Error(`Token Factory HTTP ${response.status}`);
}

for await (const chunk of response.body) {
  process.stdout.write(Buffer.from(chunk).toString("utf8"));
}
```

## Supported request fields

The POC contract intentionally exposes a small subset. Fields outside this table are unsupported unless Token Factory confirms them in writing.

| Method | Supported request fields |
|---|---|
| Responses | `model`, `input`, `stream`, `max_output_tokens`, `temperature`, `top_p` |
| Chat Completions | `model`, `messages`, `stream`, `max_tokens`, `temperature`, `top_p` |

The current Responses contract accepts text input only. Model-specific capabilities such as image input can differ and may use Chat Completions instead. Confirm the capability assigned to your use case before sending non-text content.

## Errors and retries

Error bodies normally contain an `error` object or string. Clients must not depend on one exact error message.

| Status | Meaning | Client action |
|---:|---|---|
| `400` | Malformed JSON or invalid input | Correct the request; do not retry unchanged |
| `401` | Missing, invalid, expired, or suspended key | Load the correct key or contact support |
| `403` | Source, key, model, or action is not authorized | Confirm onboarding and model assignment |
| `404` | Model is unavailable to the current key | Refresh `/v1/models` and select a returned identifier |
| `429` | Capacity control or emergency throttling | Honor `Retry-After` when present; otherwise use backoff |
| `500` | Processing error | Retry a small number of times, then report the request time |
| `502` | Upstream model failure | Retry with backoff; report persistent failures |
| `503` | Service or model temporarily unavailable | Retry with backoff or choose another approved model |

Recommended retry policy for `429`, `500`, `502`, and `503`:

1. Retry no more than three times.
2. Use exponential backoff with jitter, for example 1, 2, then 4 seconds plus a small random delay.
3. Do not retry `400`, `401`, `403`, or `404` without changing the request or configuration.
4. Use application timeouts and cancellation. Do not leave requests open indefinitely.
5. Never log the Authorization header while troubleshooting.

Fields outside the supported request table may be rejected or ignored. Do not depend on an unlisted field even if one request returns `200`.

## Limits and service behavior

- During the first 30 days after key activation, no per-key RPM, TPM, or budget limit is configured by default. This is not a capacity guarantee.
- Planned limit changes will be communicated at least two business days in advance.
- Token Factory may apply immediate throttling or suspension when security, abuse, or capacity risk requires it.
- Key validity defaults to 90 days and can be renewed.
- Keys are provisioned by Thanawat Kaewboworn only.
- A key can be activated while Security or RAI approval evidence is pending. The approval reference must be supplied within 10 business days of activation or the key may be suspended.
- The model catalog and model behavior can change during the POC. Clients must check `/v1/models` and handle unavailable models.
- The POC has no formal backward-compatibility commitment. Validate critical client behavior before each release.

## Data policy

- Send only data permitted by the BU's approved use case. Receiving an API key is not approval to send data.
- Operational API logging is metadata-only by default. Metadata can include key alias or hash, BU/team, model, request time, token counts, latency, status, and endpoint.
- Prompts, responses, images, audio, documents, and business payloads are not retained in operational logs by default.
- Prompt and response content may be retained only when the BU explicitly opts in to a separate evaluation dataset.
- An evaluation dataset must have separate access control and must be deleted within 90 days.
- Do not send secrets, credentials, production tokens, or data outside the approved classification and purpose.
