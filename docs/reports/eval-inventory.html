The architectural fact underneath the gap. The harness is built to take more than one application — there is an --app flag, a binding lookup, and an adapter resolved from the hashed contract string rather than a second table that could disagree with it. Its own error message even lists what a new app needs.

But exactly one binding is registered, with one adapter and one schema. That extensibility has never been exercised by a second application, and reading the code cannot settle whether it holds. That is the strongest argument for which eval to build next.

4Recommendation

  1. MNP first — the cheapest possible test of a claim we have not tested. Same modality, same scorer, label space differs by one reason class. If the harness really is multi-app this is short work; if it is not, this is where we find out cheaply rather than three applications later.
  2. sentiment_qa accuracy second — the only place we have advised production without evidence. Blocked on labelled data that does not exist; unblock it before the reasoning-off change ships anywhere.
  3. Tax invoice third — different modality but the easiest eval shape here: per-field exact match, thresholds already specified, no new statistics needed.
  4. RTR fraud fourth — highest build cost, most interesting failure surface. The prompt requires the model to count its own inputs, which is a known weak spot.
  5. Telesale last — needs genuinely new metric code. Additive negative points with per-section caps is not classification, so none of the existing scoring applies.
