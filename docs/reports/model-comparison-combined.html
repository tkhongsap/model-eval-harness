Model evaluation — can we run this labelling job on our own GPUs?

Production Gemini 2.5 Flash against models running on True’s own hardware. Marked on accuracy, tokens, speed and consistency, over two sets of evaluation test cases we wrote ourselves: a broad coverage set and deliberately messy ones. Every figure comes from the recorded logs of this evaluation.

An evaluation on written test cases · no production traffic · no customer data

1. What we tested it on

We wrote two sets of evaluation test cases. Each test case is a Thai call-centre transcript we made up, with the right answers filled in by hand, so we can mark a model's homework against them. Nothing here is a production call: no customer data, no real transcripts, nothing confidential.

A note on wording. Below, “call” means the conversation a test case depicts — never a real one. Everything that was actually run was an evaluation test case.

Two sets rather than one because a model can look good on ordinary calls and fall apart on awkward ones. One caveat on that logic, up front: the two sets were run on different days, and the Gemini we measured against did not behave the same way on both (section 6). Read the second set as a second attempt to find a difference, not as independent confirmation of the first.

Set A · 138 test cases retention_v3

The coverage set

One of everything that can go wrong. Thirty straightforward calls as a baseline, and then eight deliberate faults, each isolated so a failure can be blamed on a cause: Thai negation and who-said-what (a save-shaped phrase spoken by the agent, not the customer), speech-to-text garble left in on purpose, Thai and English mixed mid-sentence, quotes that break JSON output, two plausible reasons where only one is correct, and long transcripts — up to about 15,600 characters.

If a model cannot do this set, it cannot do the job.

Set B · 50 test cases retention_challenge_v1

The messy-conversation set

The sentences are easy; the conversation is the problem. Five situations, ten calls each. The customer rang last week and that changes the answer. They agree to stay, then change their mind. They get put on hold, transferred, interrupted, and wander off topic. They discuss several products in one call, ending differently on each. And they negotiate an ending that sits right on the line between two labels.

Every call is exactly 18 turns, and more of them carry several products — 11 of these 50, against 8 of the 138 in set A. Doing well here means following a conversation, not just reading a sentence.

Here is exactly what is in each set, and why each part is there.

What was held constant, and what was not. Held constant: the prompt, the ground truth, the scoring code and 3 repeats. Not held constant — the reference was reached through OpenRouter rather than the production path, so its latency and price are a router's; the Qwen arms are fp8-quantised builds (qwen3.8-27b-fp8) while Gemma is gemma-4-12b-it; and reasoning effort is none on the reference against provider-default on ours. Quantisation and reasoning effort can move accuracy, so read this as a comparison of models as deployed — the operationally useful question, but a different serving choice could change these numbers.

2. What each model had to get right

For every call the model reads the transcript and fills in three things. Each is marked separately, and they are never rolled into a single score — they are counted over different sets of rows, so an average of the three would not mean anything.

Call outcome

save / churn / unknown / undefined

What the call ended as. Marked once per product, so a call about two products is marked twice — which is why set A has 150 things to mark across 138 test cases, and set B 64 across 50.

Reason

11 values, up to 3 per call

Why. Marked over every row the model produced as well as every row it should have, so the number of things to mark moves with the model (157–164 in set A): a model that over-labels adds rows to its own denominator.

Product

postpaid / TOL / TVS / unknown

Which product. Scored per call as an exact set — two right out of three counts as wrong. 138 and 50.

Each transcript was sent 3 times. The accuracy figures are scored on the first run only; the other two are what section 6 measures. An F1 averaged over repeats would hide exactly the variation that section exists to show.

How the verdict is decided

On most calls both models give the same answer, and those say nothing about which is better. Only the calls where one was right and the other wrong carry information.

The test is the one you would do by hand: if the models disagreed on ten calls and one model won nine of them, is that skill or luck? We call it real only if a split that lopsided would happen less than once in 64 times by chance — the odds of six coin flips all landing the same way. That has a consequence worth knowing: below six disagreements no result can clear the bar, however one-sided, and the margin needed grows with the number of disagreements. “Too few to call” is not a pass and not a tie. It means the two models agreed so often that the test could not separate them even in principle. 5 of the 12 rows above are in that state, including both of set B's strongest-looking numbers. Note also how often reason defeats both models at once: taking the same pairing in each set, Gemini and Qwen3.8 were both wrong on 46 of 138 set A calls and 19 of 50 set B calls. That label type is hard for everything we tested.

Do not read the two sets as a before and after. Gemini changed a scored label 29 times on set A and 0 times on set B, but the set changed at the same time as the date, so nothing here is controlled. The set A Gemini run is 2026-08-14 — the day it stopped being deterministic — and the set B run is 2026-08-15. That the variation had gone by the second run is suggestive, not settled; a byte-identical replay of the original workload is what would settle it. Set A's own arms are not one day either: Gemini, Qwen3.6 and Gemma ran 2026-08-14, Qwen3.8 ran 2026-08-15.
On set A every arm rewrote its wording constantly and what differed was whether the rewrite reached a label: Qwen3.8 moved its text on 127 of 138 calls but a scored label only 6 times. This is not a self-hosting artefact — on the same set the hosted reference rewrote 111 and moved a scored label 29 times, the highest of any arm here.

7. What is missing, and why

Gemma 4 12B was not measured on set B

Gemma 4 12B was attempted and is NOT in this comparison: its vLLM backend at 10.94.154.104:8000 went down between the smoke test and the arm, and all 150 calls returned HTTP 500 from the gateway. The model stayed listed in /v1/models throughout. Run 20260815-223809Z-e20-chal-gemma is kept as the record of that failure. Add the arm back to this config and regenerate once the backend returns.

This is an outage, not a result. Gemma's accuracy on set B is unmeasured, and nothing here should be read as evidence about it either way. Re-running takes about eight minutes and carries no metered charge, once that backend is restarted.

Qwen3.6 27B is absent for a different reason

It was measured on set A — 0.962 / 0.821 / 0.932 — and has since been replaced on the GPU host by Qwen3.8, so it cannot be run on set B. A deployment decision, not a failure. The upgrade is not measurably an improvement in accuracy: Qwen3.8's F1 is higher on all three label types, but the paired test between them returns too few to call, no real difference and too few to call — none of the three differences is resolvable, and on reason the disagreements lean the other way (Qwen3.6 right on 16 calls Qwen3.8 missed, against 9 the other way). What did improve is consistency: 6 scored-label changes against 8.

Bottom line

Qwen3.8 27B on our own GPU is not measurably behind production Gemini on either set. On set A it is indistinguishable on the one label type with enough disagreements to judge, and the other two could not be called. On set B the same pattern holds on a second set built to be harder. Be precise about what that is worth: two of set B's three verdicts could not be called at all, so it is better read as a second set failing to find a difference than as corroboration. It is still worth having — a set built to be harder did not expose one either.

Gemma 4 12B is measurably behind, on the set where we have data. BEHIND on all three label types on set A — 0.929 / 0.792 / 0.933 against Gemini's 0.955 / 0.838 / 0.960. Each verdict lands exactly on its threshold, so this is the weakest form of “worse” rather than a rout — but on product Gemini won all 9 of the calls where exactly one of them was right.

If you have heard that Gemma is indistinguishable from Gemini, that came from an earlier assessment and is superseded. That reading rested on an 89-item subset of set A where two of the three label types had too few disagreements to resolve — a limit of that measurement, not evidence of parity. Measured on the full 138 test cases the verdict is BEHIND on all three. Gemma's accuracy on set B remains unmeasured; nothing here stands in for it.

What still blocks a migration decision. Three things, and the first matters most. The reference itself moved. On set A Gemini changed a scored label on 29 of 138 calls, so “indistinguishable from Gemini” describes Gemini as it behaved on 2026-08-14, not a settled incumbent — and Gemma's three verdicts each land exactly on their threshold, close enough that a reference which moved could plausibly move them. Second, throughput on our own hardware is roughly an order of magnitude below the hosted API at the concurrency we tested. Third, both sets are synthetic. Before a production call we would need this comparison against real labelled calls, with the reference measured on the same day.
