Model evaluation — our test cases on our own GPUs

An evaluation of the models we could run on True’s own hardware against the one we use in production today, across two tracks: labelling a call from its transcript, and producing that transcript from audio in the first place. Every figure below comes from evaluation test cases we wrote — no production traffic was involved. It covers accuracy, how many tokens each model uses, how fast it answers and how consistent it is.

What this is, and what it is not. An initial benchmark I built to size up these models for our own use cases. Every accuracy figure here is an upper bound — the test cases are written, and real calls are messier. It ranks these models against each other; it does not predict production accuracy, and it is not a migration verdict until we evaluate against real labelled calls.

Every item scored here is an evaluation test case — a transcript we wrote in-house for this purpose, with the right answer filled in by hand. Not production cases, no customer data, no real transcripts, no IP.

Do not read a higher accuracy figure as a win. On almost every accuracy row the models gave the same answer on nearly every test case, and where they differed there were too few disagreements to call a winner at all — a 0.002 gap can rest on a single test case. That is why the accuracy rows are not bolded. The one difference that is statistically real: Gemma 4 12B is measurably behind the production model on all three accuracy rows of the coverage set. Everything else is indistinguishable or too close to judge. The full report shows the working.

Higher is better for the three accuracy rows; lower is better for tokens, response time and answer changes. Bold marks the best figure only on the rows where the gap is large enough to mean something — tokens and answer changes.

† Response time is not a like-for-like comparison and is not bolded for that reason. The production model was called over the public internet at concurrency 8; ours ran at concurrency 4 against a single shared box. Those rows measure deployments, not models.

On the voice table, none of the three accuracy rows is bolded, and the reason is not caution. The two arms write numbers differently: the reference spells them out (“eighteen August”), the production model matches it because the prompt we wrote asks it to, and the model on our GPU writes digits. That one difference pushes character error rate against our model and entity recovery in its favour, so all three figures measure formatting as much as hearing. Reading the digits back as spoken Thai closes about two fifths of the character-error gap. The full voice report shows the working.

The two figures that are clean are the last two, and they are the ones to look at. Both models produce a broken transcript on some calls, in opposite ways, and neither says so — every call returned a normal response. The production model silently drops whole passages on two calls; ours runs away into repetition on one, emitting seventeen times more text than the audio contains. That one call is 83% of its total character error, which is why the row above it excludes it. Re-running it reproduced byte-for-byte, so it is a property of the model on that audio, not luck.

Two models have no result on the second set, for different reasons. Gemma was attempted, and the GPU serving it was already down when the run started, so every request came back a server error. Its accuracy on that set is therefore unmeasured, not zero — the outage is a fact about our box, not about Gemma. Qwen3.6 was replaced on the host before this set existed, so it was never in that comparison.
